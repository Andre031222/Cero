\begin{abstract}
Test suites written alongside an implementation assert the behaviour that
implementation was designed to exhibit, and are therefore weak instruments for
finding requirements the developer never represented. We report a controlled
instance. An HTTP/1.1 and HTTP/2 server that passed its own suite of 434 checks
was subjected to three further instruments --- 23 conformance vectors written
directly from RFC~9112 and RFC~9110, the third-party suite h2spec, and review by
an external consumer --- and to deployment behind a reverse proxy. The original
suite accounted for none of the fourteen defects the others found: four protocol
violations, one of them a precondition for request smuggling; two defects whose
common shape is an unexercised \emph{exit path} rather than an unexercised line,
one of which is a second smuggling precondition; six security findings including
two resource-exhaustion paths reachable without credentials; and two defects
existing only in the program's relationship with its environment. We characterise which defect classes each instrument reaches,
propose counting exit paths --- protocol version by response kind by message
ordering --- as a coverage criterion for protocol components, and report that
for defects that are races a conformance suite run once per commit samples
rather than decides: fifty-five consecutive passes coexisted with a defect that
an external suite failed on two of three continuous-integration runs. The
implementation, the vectors and the scripts reproducing every result are public.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

A test suite written alongside an implementation tends to assert what the
implementation was built to do. It is a poor instrument for finding what the
specification requires and the implementation never considered.

This paper reports a controlled instance of that gap. We took an HTTP server
that passed its own suite of 434 checks and subjected it to two independent
conformance instruments: a set of vectors we wrote directly from the text of
RFC~9112 \cite{rfc9112} and RFC~9110 \cite{rfc9110}, and h2spec
\cite{h2spec}, an existing suite for HTTP/2 \cite{rfc9113}. We report what each
instrument found, what an external security audit found, and --- the part we
believe generalises --- what distinguishes the defects that the
implementation-derived suite could never have found.

\paragraph{Contributions}
\begin{enumerate}
  \item A reusable set of 23 conformance vectors for HTTP/1.1 servers covering
        13 clauses of RFC~9112 and RFC~9110, sent as raw bytes and each citing
        the clause it enforces.
  \item The four violations the vectors exposed in an implementation that
        already passed its own tests (Section~\ref{sec:violations}).
  \item Two defects of the request-smuggling family whose common shape is an
        \emph{unexercised exit path}, not an unexercised line
        (Section~\ref{sec:exitpaths}), one of which was intermittent and
        therefore invisible to a pass/fail criterion applied once.
  \item A characterisation of which defect classes each instrument detects, and
        the cost of each (Section~\ref{sec:discussion}).
\end{enumerate}

\section{Background and related work}
\label{sec:background}

\subsection{Parsing discrepancies and request smuggling}

The security consequence of HTTP parsing divergence is well established. Grenfeldt
et al.~\cite{grenfeldt2021} tested six proxies and six servers empirically,
finding nineteen vulnerable parsing behaviours and, by pairing proxies with
origins, six workable attacks. Huang et al.~\cite{huang2022} approach the same
problem from the defensive side, proposing a reverse proxy that rejects requests
not conforming to the RFC before forwarding them. More recently, parsing
discrepancies have been shown to bypass web application firewalls
outright~\cite{waffled}.

The closest work to ours in method is the HTTP Garden~\cite{httpgarden}, a
coverage-guided differential fuzzer for HTTP/1.1 origin servers. It reported over
one hundred parsing bugs across widely deployed servers, of which sixty-eight
were fixed and thirty-nine assigned vulnerabilities. Differential fuzzing and
specification-derived vectors are complementary: a differential fuzzer finds
where implementations \emph{disagree with each other}, which requires several
implementations and cannot label either side as wrong; vectors written from the
specification find where an implementation disagrees with \emph{the text}, which
works on a single implementation and yields a clause to cite. Two of the four
violations we report --- \emph{absolute-form} and \emph{asterisk-form} request
targets --- are cases where our server would have agreed with a permissive peer
and disagreed only with the RFC.

\subsection{Conformance suites}

For HTTP/2 a free conformance suite exists and is widely used~\cite{h2spec}.
For HTTP/1.1 the situation is thinner but not empty: h1spec~\cite{h1spec}
targets RFC~9112 and 9110 explicitly and in the same spirit, though it is recent,
has a short revision history and was written primarily to test one project. Our
vectors were written independently of it and before we were aware of it, which
we state because it bears on their independence rather than on their value: two
sets of vectors derived separately from the same specification text agreeing on
a clause is weak evidence, whereas either finding a violation is strong
evidence.

\subsection{Positioning}

The studies above examine many implementations from the outside and report
aggregate vulnerability counts. We report the complementary case: one
implementation examined from the inside by four instruments of differing
provenance, where the defects each instrument reached can be attributed and the
suite that found none of them can be inspected.

\section{Subject system and instruments}
\label{sec:subject}

\subsection{Subject}

Cero is a Java web framework with its own HTTP/1.1 and HTTP/2 server and no
runtime dependencies beyond the JDK. The HTTP module comprises 43 classes and
6\,752 lines, exercised by 434 checks of the project's own suite. The complete
system is public.

\section{Violations found by specification-derived vectors}
\label{sec:violations}

The 23 vectors exposed four violations in a server that passed its own suite:

\begin{enumerate}
  \item \textbf{\emph{absolute-form} request targets rejected} (RFC~9112 §3.2.2).
        A server must accept \texttt{GET http://host/path HTTP/1.1}; ours
        returned 400.
  \item \textbf{\emph{asterisk-form} rejected} (RFC~9112 §3.2.4).
        \texttt{OPTIONS * HTTP/1.1} was not recognised.
  \item \textbf{\texttt{chunked} accepted outside the final position} of
        \texttt{Transfer-Encoding} (RFC~9112 §6.1). Accepting it is a known
        precondition for request smuggling when an intermediary disagrees with
        the origin about where a message ends.
  \item \textbf{Null bytes admitted in header values} (RFC~9110 §5.5).
\end{enumerate}

None of the four is exotic. All four survived a suite written by the same
authors who wrote the parser, because that suite asserted the behaviour the
parser was designed for.

\section{Unexercised exit paths}
\label{sec:exitpaths}

Two further defects share a shape that we argue is the more interesting
finding, because neither is reachable by adding assertions to the existing
suite.

\subsection{The session cookie over HTTP/2}

Two sibling implementations of the same response interface existed, one per
protocol version. Only the HTTP/1.1 one asked for the pending session cookie.
Over HTTP/2, therefore, no client could establish a session; and with no
session there is no CSRF token, so every write returned 403 attributing the
failure to the wrong cause.

All 432 checks of the module passed throughout. Every one of them entered over
HTTP/1.1.

\subsection{Body validation after the response}

Completing a response closes the local half of an HTTP/2 stream, not the stream
(RFC~9113 §5.1) \cite{rfc9113}. The implementation removed the stream from its
table as soon as the request handler returned. A \texttt{DATA} frame arriving
afterwards therefore found no stream, and the check that the received body
matches the declared \texttt{content-length} --- the check that prevents the
smuggling precondition --- was skipped.

The defect was \emph{intermittent by construction}: it manifested only when the
response won the race against the request body, and the project suite passed
throughout. Its observed behaviour under h2spec is worth stating precisely,
because it is the point of this subsection
(Table~\ref{tab:intermittent}).

\begin{table}[ht]
\centering
\caption{Observed failures of h2spec case 8.1.2.6.1 before and after the fix.
         Warm-up state dominates: the defect hid whenever the JVM had already
         been exercised.}
\label{tab:intermittent}
\begin{tabular}{llrr}
\toprule
Build & Condition & Runs & Failures \\
\midrule
Before fix & continuous integration, cold JVM & 3  & 2 \\
Before fix & local, cold JVM                  & 5  & 1 \\
Before fix & local, warm JVM                  & 55 & 0 \\
After fix  & local, warm JVM                  & 42 & 0 \\
\bottomrule
\end{tabular}

Two consequences follow. First, a conformance tool run once per commit is a
\emph{sampling} instrument, not a decision procedure, when the defect is a
race. Second, and less obvious, fifty-five consecutive passes were not evidence
of correctness: the same fifty-five passes occurred with the defect present.
Establishing that the fix worked required reverting it and observing the
deterministic test fail, which is the only step that distinguishes a repair from
a coincidence.

\subsection{Why line coverage cannot see either}

In both cases every line was executed by some test. What was never traversed was
a \emph{path out of the system}: a response emitted over the second protocol, a
frame arriving after the handler returned. We therefore propose counting exit
paths --- protocol version $\times$ response kind $\times$ ordering --- as the
coverage criterion for this class of component.

\section{External audit}
\label{sec:audit}

The framework's first external consumer was a university portal. Its developer,
who had not written the framework, reviewed the source and produced eleven
findings, two of them exploitable from outside without credentials. Six are
security defects and are listed in Table~\ref{tab:audit}; the remaining five
were API and functional gaps.

\begin{table}[ht]
\centering
\caption{Security findings from the external review. None was reachable by the
         project's own suite at the time.}
\label{tab:audit}
\begin{tabular}{p{0.26\linewidth}p{0.62\linewidth}}
\toprule
Finding & Mechanism \\
\midrule
Session fixation &
  The identifier held before authentication remained valid afterwards; the CSRF
  token travelled with it. \\
Memory exhaustion via static files &
  The classpath resource cache stored \emph{absences}, keyed by the requested
  path. Every 404 left two permanent entries in an unbounded map, so an
  unauthenticated loop filled the heap. \\
Rate limiter bypass &
  The path formed part of the bucket key, so spreading the load across invented
  URLs multiplied the quota while growing the map. \\
Symbolic links followed &
  \texttt{readAttributes} followed them although the adjacent line declared
  otherwise. \\
No absolute session lifetime &
  Only inactivity was counted, so a session touched occasionally never expired. \\
CSRF exemption by bare prefix &
  Exempting \texttt{/api/public} also exempted
  \texttt{/api/publicSECRET}. \\
\bottomrule
\end{tabular}
\end{table}

Two of these --- the unbounded cache and the rate-limiter key --- are resource
exhaustion reachable without credentials. Both arise from the same modelling
error: a cache key chosen from attacker-controlled input with no bound on
cardinality.

Two additional defects appeared only after deployment behind a reverse proxy: a
session cookie issued without \texttt{Secure}, because the application did not
know TLS was terminated upstream, and a deployment script that erased the
certbot HTTPS block when rewriting the virtual host. Neither is reachable by any
instrument applied to the program alone.

\section{Discussion}
\label{sec:discussion}

\subsection{What each instrument can and cannot see}

The four instruments are not interchangeable, and the boundary between them is
not effort but \emph{provenance}.

A suite written alongside an implementation encodes the developer's model of the
problem. It detects regressions against that model, which is valuable and is
why such suites exist. It cannot detect a requirement the developer never
represented --- and \emph{absolute-form} request targets, an absolute session
lifetime and a body arriving after a response are all requirements that were
never represented here.

Specification-derived vectors detect exactly that gap, at a cost proportional to
the specification's size rather than the implementation's. Twenty-three vectors
covering thirteen clauses is a few hours of work and is not a complete
conformance suite; it was nonetheless sufficient to find four violations.

Third-party suites add independence and, as Section~\ref{sec:exitpaths} shows,
find defects in the interaction between protocol state machines and application
concurrency that a specification reading alone would be unlikely to reach.

External review found what all three automated instruments missed: resource
exhaustion arising from a design decision --- an unbounded cache keyed by
attacker-controlled input --- rather than from a wrong branch. Two of the six
findings reduce to that single modelling error, which suggests reviewing
\emph{key provenance and cardinality} as a checklist item rather than
discovering each instance separately.

\subsection{Counting exit paths}

We propose, for protocol-handling components, a coverage criterion of
\emph{exit paths}: the cross product of protocol version, response kind and
message ordering. In the subject system that criterion would have flagged both
unexercised-path defects before either shipped. Both were invisible to line
coverage, since every line involved was executed by some test.

\subsection{Recommendation}

For implementers of HTTP servers, the ordering that our evidence supports is:
write specification-derived vectors before growing the implementation-derived
suite; run third-party conformance suites repeatedly rather than once, since a
single pass does not distinguish a correct implementation from a race that
happened not to lose; and treat deployment behind a proxy as an instrument in
its own right, because two of our defects existed only in the relationship
between the program and its environment.

\section{Threats to validity}
\label{sec:threats}

\paragraph{Single subject}
The findings come from one implementation. We report the shape of each defect
rather than a frequency, and make no claim about how often these defects occur
in HTTP servers generally.

\paragraph{The vectors are ours}
The 23 vectors were written by the same authors as the implementation, which
weakens their independence. We mitigated this by writing them from the RFC text
without reference to the code, and by cross-checking HTTP/2 against a suite we
did not write \cite{h2spec}. The audit is the only fully independent instrument.

\paragraph{Intermittent defects and sampling}
The failure counts in Table~\ref{tab:intermittent} are observations from a
small number of runs on two machines, not an estimated failure rate. We report
them to characterise the defect's dependence on warm-up state, not to quantify
its probability.

\section{Conclusion}
\label{sec:conclusion}

We subjected an HTTP server that passed its own 434-check suite to three further
instruments and to deployment behind a reverse proxy. Together they found
fourteen defects that the original suite did not, including four violations of
RFC~9112 and RFC~9110, two preconditions for request smuggling, and two
resource-exhaustion paths reachable without credentials.

The dividing line is provenance, not effort. A suite written from an
implementation asserts the behaviour the implementation was built to exhibit,
and is structurally unable to detect a requirement that was never represented.
Twenty-three vectors written from the specification text --- a few hours of work
--- found four such requirements.

We also report a methodological observation with practical consequences: for
defects that are races, a conformance suite executed once per commit samples
rather than decides. Fifty-five consecutive passes coexisted with the defect
present, and only reverting the repair and observing a deterministic test fail
distinguished a fix from a coincidence.
